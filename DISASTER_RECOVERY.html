1What Is Disaster Recovery?

Disaster Recovery (DR) means having a backup copy of your entire application ready in a different physical location, so that if something catastrophic happens to your main infrastructure — a data-centre power failure, a regional AWS outage, accidental data deletion — you can switch all users over to the backup within minutes.

StockMind serves real-money stock-market data. Any extended outage directly harms users. This DR system is designed so that a full region failure causes at most 15–20 minutes of downtime and no more than 24 hours of data loss.

Simple explanation

Think of it like a generator for your house. While mains power is on the generator sits idle — costing very little. The moment power cuts, it kicks in automatically. Here the "generator" is an entire second copy of StockMind sitting in Mumbai (ap-south-1), silent and cheap, ready to start in minutes if Hyderabad (ap-south-2) goes down.

2DR Strategy: Pilot Light

AWS defines four DR strategies from cheapest to fastest: Backup & Restore → Pilot Light → Warm Standby → Multi-Site Active/Active. We use Pilot Light.

StrategyHow it worksRTOMonthly Cost
Backup & RestoreSnapshots only. Full rebuild on disaster.Hours–days~$10
Pilot Light ✓Infrastructure exists, ECS at 0, DB stopped. Lambda starts it.15–20 min~$92
Warm StandbyMinimal live instances running always.5–10 min~$220
Multi-Site Active/ActiveFull mirror, traffic split 50/50.<1 min~$600

Why Pilot Light?

Pilot Light is the sweet spot for a startup: it costs 85% less than active/active but recovers 10× faster than pure backups. The ECS services are set to desired_count = 0 (zero Fargate charges) and the TimescaleDB EC2 is stopped (only the disk is billed at ~$16/month). When disaster hits, a Lambda function starts everything within 15 minutes.
HCL — pilot light ECS service 
# desired = 0 in pilot_light → zero Fargate cost
resource "aws_ecs_service" "backend" {
  name          = "${var.name}-backend-svc"
  cluster       = aws_ecs_cluster.dr.id
  desired_count = local.desired   # 0 in pilot_light

  lifecycle {
    ignore_changes = [desired_count]  # Lambda manages scaling
  }
}

Why only one NAT Gateway in DR?

In production we pay for two NAT Gateways (one per Availability Zone) so that if an AZ dies, outbound internet still works from the other AZ. In the DR region, the whole point is that this region is only handling traffic during a major disaster — the chance of an AZ failure simultaneously with a region failure of the primary is extremely small. So one NAT Gateway saves about $32/month with negligible additional risk.
HCL — single NAT gateway in DR 
# Cost optimisation: 1 NAT in DR vs 1-per-AZ in primary
resource "aws_nat_gateway" "dr" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id  # single NAT in AZ-a
  depends_on    = [aws_internet_gateway.dr]
}

5DR Compute (dr_compute module)

ECS Fargate — Pilot Light (desired_count = 0)

All four ECS services (frontend, backend, celery-worker, celery-beat) have desired_count = 0 in pilot-light mode. The task definitions, IAM roles, security groups, and load balancer rules are all pre-created — only the actual Fargate tasks are absent. This means startup from 0 → running takes only the time to pull the Docker image and pass the health check (typically 3–5 minutes per service).

TimescaleDB EC2 — Stopped State

The EC2 instance is created normally but then stopped via a Terraform null_resource local-exec. While stopped, AWS charges only for the attached EBS volume (~$16/month for 200 GB gp3). The instance retains its private IP and ENI, so the connection strings stored in Secrets Manager remain valid — no updates needed at failover time.

Redis — Smaller Instance in DR

Redis is kept running (unlike ECS which is at 0) because it cannot be "stopped". We use a cache.t4g.micro in DR vs cache.t4g.small in primary. At failover, the application connects to Redis in DR — it starts with a cold cache but recovers within seconds as requests populate it.

How does the ECS start-up work at failover?

The failover Lambda calls ecs:UpdateService for each service, setting desiredCount to the target number (e.g., 2 for frontend, 2 for backend). ECS schedules those tasks on Fargate. Each task pulls its Docker image from ECR (which already has the replicated image), starts the container, and the ALB waits for the health check to pass. The whole process takes 3–8 minutes per service, running in parallel. Total from zero to fully healthy: about 10–12 minutes.
HCL — stop EC2 after creation (pilot light) 
resource "null_resource" "stop_timescale_pilot_light" {
  count = var.dr_strategy == "pilot_light" ? 1 : 0

  provisioner "local-exec" {
    command = "aws ec2 stop-instances \
      --instance-ids ${aws_instance.timescale.id} \
      --region ${var.dr_region} || true"
  }
}

Important: TimescaleDB RPO is up to 24 hours. This means up to one day of market data could be lost in a worst-case region failure. For production, consider reducing the backup schedule to every 6 hours for more granular recovery points.

What is RPO and why does it matter?

RPO (Recovery Point Objective) is the maximum amount of data you can afford to lose. If your TimescaleDB backup runs at 02:00 UTC and disaster strikes at 23:00 UTC, you lose 21 hours of time-series data. For stock data this means charts and analytics would be missing data for that period. The application would still work — users could still log in and trade — but historical charts would have a gap.
HCL — S3 Cross-Region Replication rule 
resource "aws_s3_bucket_replication_configuration" "primary_to_dr" {
  provider = aws.primary
  bucket   = var.primary_s3_bucket_name
  role     = aws_iam_role.s3_crr.arn

  rule {
    id     = "replicate-all-to-dr"
    status = "Enabled"
    filter {}  # replicate all objects

    destination {
      bucket        = var.dr_s3_bucket_arn
      storage_class = "STANDARD_IA"  # cheaper in DR
    }
  }
}

7DNS Failover — Route 53 (dr_routing module)

Route 53 is configured with failover routing policy — the same DNS name (stockmindai.xyz and api.stockmindai.xyz) has two records: one pointing to the primary ALB (marked PRIMARY) and one pointing to the DR ALB (marked SECONDARY). Route 53 continuously monitors the primary ALB via health checks. When three consecutive checks fail (90 seconds), Route 53 automatically starts returning the DR ALB's IP address.

Route 53 health checks run from AWS PoPs globally (not from your VPC). CloudWatch alarms that monitor health checks must be in us-east-1 — this is an AWS requirement. The dr_routing module uses a separate aws.us_east_1 provider alias for this.
HCL — Route53 failover record pair 
# PRIMARY — normal traffic goes here
resource "aws_route53_record" "api_primary" {
  zone_id        = var.hosted_zone_id
  name           = var.api_domain_name
  type           = "A"
  set_identifier = "primary"
  alias {
    name    = var.primary_alb_dns
    zone_id = var.primary_alb_zone_id
    evaluate_target_health = true
  }
  failover_routing_policy { type = "PRIMARY" }
  health_check_id = aws_route53_health_check.primary_api.id
}

# SECONDARY — only used when PRIMARY health check fails
resource "aws_route53_record" "api_dr" {
  zone_id        = var.hosted_zone_id
  name           = var.api_domain_name
  type           = "A"
  set_identifier = "dr"
  alias {
    name    = var.dr_alb_dns
    zone_id = var.dr_alb_zone_id
    evaluate_target_health = true
  }
  failover_routing_policy { type = "SECONDARY" }
}

DNS TTL and failover speed

When Route 53 detects a failure, it stops returning the primary ALB's IP. The speed of failover depends on the DNS TTL (Time-To-Live). If your domain has a TTL of 60 seconds, browsers will check for a new IP every minute — so they'll switch within 60 seconds of Route 53 updating. The health check itself takes about 90 seconds (3 checks × 30 seconds). Total DNS failover time: 2–4 minutes. The Lambda startup of ECS adds another 10–15 minutes, so the full user-visible RTO is about 15–20 minutes.

8Automated Failover (dr_automation module)

Failover is fully automated via three AWS services working together:

  1. Route 53 health check detects the primary ALB is unhealthy
  2. CloudWatch alarm transitions to ALARM state (us-east-1)
  3. EventBridge rule matches the alarm state-change event and invokes the Lambda
  4. Lambda starts TimescaleDB EC2, scales all ECS services to desired counts, publishes SNS
  5. SNS emails the operations team
Python — Lambda failover core logic 
def handler(event, context):
    # Step 1: start TimescaleDB EC2
    ec2.start_instances(InstanceIds=[TIMESCALE_INSTANCE])
    waiter = ec2.get_waiter("instance_running")
    waiter.wait(InstanceIds=[TIMESCALE_INSTANCE])

    # Step 2: scale ECS services from 0 → desired
    for svc_key, svc_cfg in SERVICES.items():
        ecs.update_service(
            cluster=ECS_CLUSTER,
            service=svc_cfg["name"],
            desiredCount=svc_cfg["desired"],
        )

    # Step 3: notify operations team
    sns.publish(TopicArn=SNS_TOPIC_ARN,
                Subject="[StockMind DR] Failover SUCCESS",
                Message="All DR services started.")

Why EventBridge instead of calling Lambda directly from CloudWatch?

EventBridge gives us a clean event-driven architecture. The CloudWatch alarm publishes its state change as an event. EventBridge acts as a router — in the future you could add more targets (Slack webhook, PagerDuty, Jira ticket) without modifying the Lambda. It also gives you a full audit trail in CloudTrail of exactly when each step triggered.

9Production Disaster Scenarios

These are the 10 real-world failure scenarios this DR architecture covers, with the specific recovery mechanism for each.

🌍 Full Region Failure RTO: 15–20 min

AWS ap-south-2 becomes entirely unavailable. Route53 health check fails → CloudWatch alarm → EventBridge → Lambda scales DR ECS + starts TimescaleDB. DNS automatically points to Mumbai.

💾 Database Corruption RTO: 30–60 min

TimescaleDB data is corrupted (bad migration, ransomware, operator error). Restore from latest AWS Backup cross-region snapshot in DR vault. Attach restored volume to DR EC2.

🐳 Container Image Corruption RTO: 0 min

A broken Docker image is pushed to ECR. Because tags are IMMUTABLE in both regions, the bad push creates a new tag. The ECS services still reference the old working tag. Zero impact.

🔑 Secret / Credential Breach RTO: 5–10 min

JWT secret or DB password is leaked. Update the secret in Secrets Manager (both regions). Force a new ECS deployment (aws ecs update-service --force-new-deployment). New tasks pick up new secrets.

🌐 AZ Failure (within region) RTO: 0 min

One Availability Zone in ap-south-2 fails. ECS Fargate is multi-AZ — healthy tasks in the other AZ continue serving traffic. ALB stops routing to the unhealthy AZ. No DR failover needed.

🚦 ALB / WAF Misconfiguration RTO: 2–5 min

A bad ALB listener rule blocks all traffic. Route53 health check detects the / endpoint returning non-2xx. After 3 consecutive failures (90 sec), DNS flips to DR ALB automatically.

📦 S3 Bucket Accidental Delete RTO: <1 min

Primary S3 bucket objects deleted (or bucket deleted). CRR has already copied all objects to DR S3 bucket in ap-south-1. Update the ECS task definition S3_BUCKET env var and redeploy.

🔴 Redis Failure RTO: 1–5 min

Primary Redis cluster becomes unavailable. In DR region, Redis (t4g.micro) is already running. At failover, Celery and backend connect to DR Redis. Cold cache but operational within seconds.

🏗️ Infrastructure as Code Drift RTO: 10–30 min

Someone manually changed a security group or IAM policy, breaking the application. Run terraform plan to identify drift, then terraform apply to reconcile. DR Terraform is a clean reference state.

🔒 Account Compromise / Ransomware RTO: 1–4 hrs

AWS account is compromised. DR vault snapshots are in a separate AWS Backup vault with locked recovery points (WORM). Contact AWS Support to freeze the account. Restore from vault to a new account.

What scenario is most likely in production?

In practice, 90% of "disasters" are not full region failures — they are misconfigurations, bad deployments, or secrets breaches. This DR design handles all of those without needing to invoke the full failover. The immutable container tags, Secrets Manager rotation, and multi-AZ ECS cover the common cases. Full region failover (Lambda-triggered) is the safety net for the rare catastrophic case.

How to reduce RPO below 24 hours

Change the AWS Backup schedule from daily to every 6 hours: schedule = "cron(0 */6 * * ? *)". This reduces worst-case data loss from 24h to 6h at an additional cost of ~$4/month in snapshot storage. For even tighter RPO, consider PostgreSQL streaming replication to a standby in ap-south-1 (requires removing the Docker layer and running TimescaleDB directly on EC2 or RDS).

What costs zero while in standby?

ECS Fargate tasks at desired_count=0 → $0 per month in compute. The stopped TimescaleDB EC2 (m6i.large would be ~$70/month) → $0 instance charge (only EBS disk at $16). The ECS services and task definitions exist as free metadata. The result is that the most expensive components cost nothing until the moment they're needed.

12Failover Runbook

This runbook covers both the automated path (Lambda handles it) and the manual override path (when automation fails).

Automated Failover (expected path)

T+0

Incident detected

Route53 health check fails 3× in 90 seconds. CloudWatch alarm → ALARM state. SNS email sent to alert_email.

T+2m

Lambda triggers

EventBridge fires the failover Lambda. Lambda starts TimescaleDB EC2, waits for instance_running state.

T+5m

TimescaleDB up

EC2 instance running. User-data script starts Docker container with TimescaleDB. Database accepting connections.

T+7m

ECS scaling

Lambda calls ecs:UpdateService for frontend (×2), backend (×2), worker (×2), beat (×1). ECS schedules tasks on Fargate.

T+15m

Services healthy

All ECS tasks pass ALB health checks. DR ALB returns 200 on /health. Route53 SECONDARY record is active.

T+20m

Users restored

DNS TTL expires. All new user requests resolve to DR ALB in Mumbai. StockMind fully operational from DR region.

Manual Override (if Lambda fails)

Bash — manual DR activation 
# 1. Start TimescaleDB EC2
aws ec2 start-instances \
  --instance-ids i-xxxxxxxxxxxxxxxxx \
  --region ap-south-1

# 2. Wait for instance to be running
aws ec2 wait instance-running \
  --instance-ids i-xxxxxxxxxxxxxxxxx \
  --region ap-south-1

# 3. Scale ECS services
for svc in stockmind-dr-frontend-svc stockmind-dr-backend-svc \
              stockmind-dr-worker-svc stockmind-dr-beat-svc; do
  aws ecs update-service \
    --cluster stockmind-dr-cluster \
    --service $svc \
    --desired-count 2 \
    --region ap-south-1
done

# 4. Verify (wait for RUNNING tasks)
aws ecs describe-services \
  --cluster stockmind-dr-cluster \
  --services stockmind-dr-backend-svc \
  --region ap-south-1 \
  --query 'services[0].runningCount'

When would I need the manual override?

The Lambda itself could fail to trigger if: (1) the EventBridge rule had a misconfigured event pattern, (2) the Lambda IAM role lost its EC2/ECS permissions, (3) the Lambda function itself had a bug. The manual override above achieves the same result in about the same time — it's the same AWS API calls the Lambda makes, run from your terminal.

# Invoke Lambda directly to test failover without waiting for health check
aws lambda invoke \
  --function-name stockmind-dr-failover \
  --region ap-south-1 \
  --payload '{"detail":{"state":{"value":"ALARM"}}}' \
  --cli-binary-format raw-in-base64-out \

cat /tmp/failover-response.json

How to test without affecting production users

The safest way to test is to invoke the Lambda directly (as shown above) rather than triggering the full Route53 health-check → alarm → EventBridge chain. This starts the DR services in Mumbai without changing DNS. Users stay on Hyderabad. You can then hit the DR ALB directly (by its DNS name) to verify everything works, run your smoke tests, then scale the DR ECS services back to 0 to restore the standby state.

14How to Deploy

Prerequisites: Terraform ≥ 1.5, AWS CLI configured with credentials that have IAM/EC2/ECS/S3/Route53 write access, the primary production stack already deployed and its outputs noted.
Bash — initial setup 
# 1. Clone the DR repo
git clone https://github.com/srinureddy/stockmind-dr-infrastructure.git
cd stockmind-dr-infrastructure

# 2. Copy and fill in your values
cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars — fill primary_alb_dns, secrets, route53_zone_id, etc.

# 3. Find the DR region AMI for Amazon Linux 2023
aws ssm get-parameter \
  --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --region ap-south-1 \
  --query Parameter.Value

# 4. Initialise and apply
terraform init
terraform plan   # review carefully — especially ECR replication (account-level)
terraform apply
Bash — failback to primary (after incident resolved) 
# 1. Verify primary is healthy
curl -I https://api.stockmindai.xyz/health

# 2. Scale DR services back to 0 (pilot light state)
for svc in frontend-svc backend-svc worker-svc beat-svc; do
  aws ecs update-service \
    --cluster stockmind-dr-cluster \
    --service stockmind-dr-$svc \
    --desired-count 0 \
    --region ap-south-1
done

# 3. Stop the TimescaleDB EC2
aws ec2 stop-instances \
  --instance-ids i-xxxxxxxxxxxxxxxxx \
  --region ap-south-1

# 4. Route53 will automatically route back to primary once health check passes

Terraform provider aliases explained

This DR project uses three provider aliases because resources span multiple regions: aws.primary (ap-south-2) for S3 replication role and ECR replication config which must be created in the source region; aws.dr (ap-south-1) for all DR infrastructure; and aws.us_east_1 (us-east-1) for the CloudWatch alarm on the Route53 health check, which AWS requires to be in us-east-1. Without these aliases Terraform would create everything in a single region, breaking the cross-region resources.
